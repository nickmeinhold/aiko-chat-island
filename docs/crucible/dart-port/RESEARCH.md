### A2. The SQLite seam

**Facts that hold for every candidate seam.**
- **M** There are 21 ORM tables plus `alembic_version`, defined in `domain/models.py`. A grep-built module→tables matrix (`/private/tmp/claude-501/scr/matrix.py`; W = constructor or `insert/update/delete(Model)`, R = any other reference) gives these write sets:

| table | writing modules (M, plus delegated purges) |
|---|---|
| users | accounts_service, users_service, recovery_service |
| channels | channels_service, dm_service, memberships_service (+ main.py reconcile via channels_service) |
| memberships | accounts, channels, dm, memberships services |
| messages | messages_service, channels_service (hard-delete), accounts_service (tombstone) |
| device_tokens | devices_service (register), push_service (reaper `DELETE`, `push_service.py:1183`), accounts (via `devices_service.purge_user_devices`, `accounts_service.py:204`) |
| message_reports / message_retractions | moderation_service, channels_service |
| message_reactions | reactions_service (+ accounts, channels cascades) |
| passkey_credentials / passkey_challenges | passkey_service, users_service (+ recovery reads challenges) |
| social_identities | users_service, accounts_service, rest/auth.py |
| communities / community_memberships | communities_service, accounts_service |
| signing_keys, oauth_*, social_nonces, recovery_*, user_blocks | one owning service each, plus the account purge |

- **M** **Account deletion is one transaction across about 16 tables.** `delete_user_account` runs the moderation, reactions, devices, passkey, signing-keys and recovery purges, then the communities, social, membership and user deletes, with a single `commit()` (`accounts_service.py:182-263`). `tests/test_account_deletion_cascade_guard.py:84-101` enumerates the 16 FK-to-users columns.
- **M** **Channel hard-delete** (driven by the bus topology queue, `main.py:123-151`) cascades messages, memberships, reports, retractions and reactions inside `channels_service` (imports at `:36-37`).
- **M** **SQLite here is a rollback journal, not WAL.** `busy_timeout=5000` is set per connection, and WAL is deliberately off to protect the restore drill (`db.py:37-61`). The seed DB shows `journal_mode=delete`, `foreign_keys=0`, `user_version=0` (drift probe).
  - **I** In rollback mode, a reader's SHARED lock blocks a writer's commit. Any second process's long read therefore stalls Python writes up to 5s, then they fail with SQLITE_BUSY (a 500).
- **M** **There is already a single-process lock.** `worker_guard.py` takes an exclusive `flock` on `.aiko-worker.lock` beside the DB at boot (`main.py:218`), and a second gateway process refuses to boot. Its stated reason is that the Hub keeps WS connections in per-process memory, so an active disconnect (ban, recovery re-key, account deletion) reaches only the process that handled it (`worker_guard.py:1-8`). That gap is #46 (`docs/crucible/46-cross-worker-disconnect/CAST.md`), and it is **not built**.
- **M** **Several pieces of state live in process memory and are invisible to a second process:**
  1. Hub connections and each connection's `subscribed` set (`realtime/hub.py:35-41, 79-82`).
  2. Echo suppression: `echo.mark_sent` before `bus.send`, then `echo.is_own_echo` on ingest (`realtime/ws.py:235-237`, `main.py:75`). It keys on content, standing in for `UNIQUE(channel_id, client_msg_id)` (#42).
  3. The rate limiter (module-level; the test suite resets it).
  4. APNs and FCM provider-token caches; the OAuth JWKS cache with an `asyncio.Lock` (`oauth.py:198-228`); the actuation lock (`actuation.py:359`).
  5. The single ordered topology queue (`main.py:99-151`).
- **M** **Hub calls from REST routes** (these must live with the WS process): `rest/auth.py:1152` (`disconnect_user`), `rest/recovery.py:232` (disconnect), `rest/moderation.py:215,268` (fanout and disconnect), `rest/reactions.py:102` (fanout). `realtime/ws.py` uses the hub 5 times plus `bus.send` and `push_service.schedule_wake` (`:237-256`). REST write routes by count: auth 12, moderation 7, members 5, recovery 5, others ≤2. Read-only REST modules (GET only): capabilities, channels, island, islands, legal, messages, well_known.

**The four candidate seams, measured.**

**(i) Split by route** (a reverse proxy sends some `/v1/*` paths to Dart).
- **M** Every writing route family touches `users` or `messages` or a cascade table, and five hub-coupled routes must stay with the WS owner.
- **I** A Dart process taking only the **read-only GET families** (channels, messages history, island, islands, legal, well_known, capabilities) is a reader of every table but writes none. A Dart process taking any writing family puts **two writer processes on one file**. SQLite serialises them through file locks: with busy_timeout set on both sides, that is safe at the SQL level for single statements and atomic conditional DELETEs. It breaks the invariants that live in process memory:
  - a ban, recovery or deletion handled by Dart does not disconnect sockets held by Python;
  - a membership change does not update `subscribed` sets;
  - rate limits are halved per process.
- The worker lock would also have to be lifted. That is #46's precondition.

**(ii) Split by bounded context with no shared tables.**
- **M** No such context exists for any write path, because of the account-deletion transaction (16 tables, one commit). `users` is read by 12 modules.
- **I** The only near-isolated write sets are `oauth_states`/`oauth_handoffs`/`social_nonces` (oauth broker), `signing_keys`, and `passkey_challenges`. All of them are still swept by the account purge or read by the auth paths.

**(iii) Push/APNs as an out-of-process worker.**
- **M** `push_service.py` reads channels (`:711`), memberships (`:734`), users with `banned_at IS NULL` (`:763`), device_tokens (`:804`, `:939`) and messages (`_spoken_here`, `:1238`). It **writes only device_tokens**, via the reaper's atomic conditional `DELETE … WHERE id=? AND token=? AND updated_at=? [AND updated_at<=not_reregistered_since]` (`:1155-1196`).
- **M** `devices_service` (register and refresh) and the account purge also write `device_tokens`.
- **I** That gives two writers on device_tokens. But the reaper's predicate is folded into the DELETE, and it was designed for exactly this race (a row refreshed between send and reap). This is the one place where the code already assumes a concurrent writer.
- **M** The trigger is in-process: `push_service.schedule_wake(...)` is called from `ws.py:253` after the write and the fanout, with plain values. An out-of-process worker needs a trigger channel (a queue, a poll, or the bus).
- **M** The push path also uses in-memory provider-token caches (`apns._provider_token`, `fcm._access_token`), which move with it.

**(iv) A read-only Dart sidecar.**
- **M/I** No writes, so there is no second writer. But under the rollback journal its reads take SHARED locks that delay Python commits (see above). It must also not trip `open_only` (`worker_guard.py:95`, `mode=rw`) semantics or create `-journal` files with the wrong owner (**U**, depends on the container UID).

**The second falsifier, scored.**
- **I** Only (iii) and (iv) avoid two writers on a shared table, or put a second writer only where the code is already race-designed (the device_tokens reaper). Any route split that moves a writing route (i), and every bounded-context split (ii), first needs #46 (cross-process disconnect) plus a cross-process echo key (#42).
- **I** The bus-ingest path (persist inbound, then hub fanout, then the topology reconcile) must have **exactly one owner**. Two subscribers would each persist every inbound message.

### A3. Drift over the existing database (measured with drift 2.34.0, the app's lockfile pin)

- **M** An alembic-built island DB has `PRAGMA user_version = 0` and `alembic_version = '0028'`. Alembic cannot create the file because `open_only` uses `mode=rw`. Only `scripts/build_seed.py` creates one, and the image does that at build time with Python (`Dockerfile:65-70`). Every boot runs `python -m aiko_gateway.migrate` (alembic) before uvicorn (`entrypoint.sh`).
- **M** Drift treats `user_version=0` as a new database and runs `onCreate` (`drift-2.34.0/lib/src/runtime/executor/helpers/engines.dart:550-553`, `api/db_base.dart:128-130`).
  - A plain `CREATE TABLE` fails with "table users already exists" (probed). `user_version` stays 0 because it is written only after success (`engines.dart:559-563`).
  - The default `m.createAll()` uses `CREATE TABLE IF NOT EXISTS` (`migration.dart:319,432`), so it **silently no-ops and checks nothing**.
- **M** `NativeDatabase(file, setup: (raw){…})` runs before the version check (`native.dart:78-80`). The probe (`scratch_drift/probe/bin/adopt.dart`) asserted `alembic_version=='0028'` and set `PRAGMA user_version=28`. Drift then saw `versionBefore=28` and skipped onCreate. The two bookkeeping systems are independent: alembic ignores `user_version`, and drift ignores `alembic_version` (I).
- **M** Drift never enables foreign keys itself (docs say to set the pragma in `beforeOpen`, `dsl/columns.dart:203-211`), and `foreign_keys=0` was observed after open. So ISL-0002's FK-off is drift's default. Cascades are not emulated, which means the application cascades must be ported as code.
- **M** **Drift sets no busy_timeout (default 0) and no WAL** (`native.dart`, probed `busy_timeout=0`). Without `PRAGMA busy_timeout=5000` in `setup`, a Dart writer hits SQLITE_BUSY immediately. `readPool` helps only under WAL.
  - Upstream issues: #3794, deferred transactions that both upgrade to writers get SQLITE_BUSY that busy_timeout cannot absorb (a `BEGIN IMMEDIATE` fix is on develop; whether it is in 2.34 is **U**). #3830, WAL plus the statement cache poisons the connection after BUSY_SNAPSHOT (fix version **U**).
- **M** Schema at 0028 (`scratch_drift/schema.sql`):
  - 22 tables, 48 indexes (14 explicit), 18 CHECK constraints (some named, including multi-column DM invariants on `channels`), 25 `REFERENCES` with no `ON DELETE`;
  - no triggers, views, partial indexes, STRICT or WITHOUT ROWID;
  - 7 tables carry alembic-rebuild text (`CREATE TABLE IF NOT EXISTS "users"`);
  - one integer default spelled `DEFAULT '0'`.
  - Declared types: VARCHAR ×80, DATETIME ×36, TEXT ×10, BOOLEAN ×7, INTEGER ×4, JSON ×3, BIGINT ×2.
- **M** Stored formats:
  - DATETIME is `'2026-10-25 01:02:03.000000'` (space separator, no zone, UTC by `UtcDateTime`).
  - BOOLEAN is 0/1, and JSON is text.
  - Drift's default date mode (integer) **throws** reading these. Its text mode reads them as UTC but **writes** `2026-10-25T01:02:03.000Z`. `'T' > ' '`, so mixed rows mis-sort in text comparison. A custom type is needed (`IslandDateTime` in the probe). Whether SQLAlchemy parses drift's format is **U**.
- **M** `m.alterTable(TableMigration(...))` is SQLite's 12-step rebuild in one transaction (`migration.dart:161-315`).
  - It recreates the table **from drift's Dart definition**, not from the old SQL, then re-runs the saved index and trigger SQL. It skips the FK check and the version bump (`:310`), and views are "not reliably handled" (`:156`).
  - **I** Named CHECKs, `DEFAULT '0'` and column order survive only if the drift table reproduces them verbatim.
- **M** `validateDatabaseSchema` (drift_dev, `migrations_native.dart:57`) is a **runtime** check that diffs live `sqlite_master` against an in-memory `createAll`. Details (`find_differences.dart`):
  - Columns are matched by name.
  - Types are compared by affinity: VARCHAR equals TEXT, and BOOLEAN, DATETIME and JSON all fall to REAL.
  - Column constraints must match exactly, in order; only these can be disabled (`validateColumnConstraints:false`).
  - Table constraints must match **in exact order and are always checked** (:142-150).
  - Indexes and triggers must match exactly.
  - It is **one-directional** by default: `validateDropped:false` ignores extra live objects, including `alembic_version` and undeclared `ix_*` indexes.
- **M** An idiomatic drift `users` table **fails** validation (type, `DEFAULT '0'` vs `DEFAULT 0`, explicit NULL, inline vs table-level UNIQUE, 1 vs 4 table constraints). A **faithful** copy **passes**, using per-column `customConstraint('<alembic text>')`, a `CustomSqlType` named `DATETIME`, and `customConstraints` in alembic's order. Only `users` was verified end to end. `channels` (multi-column `substr` CHECKs) and the 7 rebuilt tables are **U**.
- **M/I** `make-migrations` / `schema dump|generate|steps` form a build-time-snapshot plus test-time chain that checks drift against **its own past snapshots**, never against an external schema. Seeding it at v28 from a DB drift did not build is **U**. Known gaps:
  - #3219: exported snapshots dropped `check()`, so migration tests passed while live validation failed.
  - #3694: step `createTable` ignored `customConstraints` (fixed on develop; whether 2.34 has it is **U**).
- **M** The app (`../aiko_chat_app`) uses **drift runtime only, with no codegen and no drift_dev**:
  - `allTables => const []` and raw-SQL DDL (`lib/features/chat/data/cache/drift_cache.dart:15-24,163-172,262`);
  - `schemaVersion => 6` with a hand ladder of `ALTER TABLE ADD COLUMN` (`:246,266-323`);
  - tests that hand-set `PRAGMA user_version` and reopen (`test/drift_migration_test.dart:79`), and that compare `PRAGMA table_info` to a const map (`test/drift_cache_schema_test.dart:33-42`).
  - It is a single-process, rebuildable cache. No rebuild migration has ever been needed there, so little of it transfers (I).
- **M** The Python test suite builds its schema with `Base.metadata.create_all`, **not alembic** (tests/conftest.py, per the test-suite survey). `tests/test_check_constraints.py` exists because the two schemas differ. Any Python-seeded DB handed to Dart must come from the alembic path.

### A4. WebAuthn server: what we actually use

- **M** The dependency is `webauthn>=2.0` (`pyproject.toml:57`), locked and installed at **3.0.0** (`uv.lock:735`). Upstream 3.0.1 (2026-09-25) rejects non-string `fmt`. Calls:
  - `generate_registration_options`, `generate_authentication_options`, `options_to_json`, `verify_registration_response`, `verify_authentication_response` (`domain/passkey_service.py:51-57`, `:168-255`);
  - recovery re-uses `verify_registration` (`recovery_service.py:324-345`).
- **M** Our policy:
  - resident key REQUIRED;
  - UV REQUIRED by default (`passkey_require_user_verification`, `config.py:597`), and UP is always required;
  - algorithms at the default: EdDSA −8, ES256 −7, RS256 −257;
  - `attestation` is not passed, so "none" is requested;
  - `allowCredentials` is empty (usernameless);
  - the user handle is 16 random bytes and is **never stored** (Android rejected 64 bytes, #1957).
- **M** **Requesting "none" does not stop attestation processing.** py_webauthn dispatches on whatever `fmt` arrives (none, fido-u2f, packed, tpm, apple, android-safetynet, android-key; `verify_registration_response.py:217-288`). With no trust roots passed, chain validation returns True for every format except Apple, which carries its own root (`validate_certificate_chain.py:31-32`, `apple.py:45`).
  - **U** Which formats reach prod: `fmt` is not stored. The stored `aaguid` column is the cheapest way to find out.
- **M** Origins are `["https://<rp_id>", *passkey_extra_origins]` (`passkey_service.py:69-74`), compared by exact string. In prod the extras are three `android:apk-key-hash:` values from the compose default (`docker-compose.yml:204`). These are **a second, hand-maintained list** that currently agrees with `PASSKEY_ANDROID_CERT_SHA256` (`:192`); base64url(sha256) was recomputed and all three match. They are not derived from one another.
- **M** Storage:
  - `passkey_credentials`: `credential_id` String(512) UNIQUE, base64url without padding; `public_key` Text, base64url of **py_webauthn-re-encoded** COSE bytes, not the authenticator's original bytes; `sign_count` BigInteger; `transports` JSON; `aaguid`.
  - The sign-count rule rejects if either count is >0 and new ≤ stored (`verify_authentication_response.py:158-166`).
  - Challenges (`passkey_challenges`): the PK is the challenge itself (32 random bytes, b64url), with `operation` CHECK, 300s TTL (`config.py:589`) and a single-use guarded UPDATE decided by rowcount (`passkey_service.py:95-146`).
- **M** **Existing bug.** The finish handlers catch only `InvalidRegistrationResponse` and `InvalidAuthenticationResponse` (`rest/auth.py:551,623,686`; `rest/recovery.py:174`). py_webauthn also raises `InvalidJSONStructure`, `InvalidBackupFlags`, `InvalidPublicKeyStructure`, `UnsupportedAlgorithm`, `InvalidCertificateChain`, and a bare `KeyError` from COSE decoding. Reproduced: a missing `rawId` produces a 500. The comment at `auth.py:552` ("wraps parse failures too") is false. It fails closed, so it is not a bypass.
- **M** Checks that py_webauthn 3.0.0 does **not** do:
  - `crossOrigin` is parsed and ignored; `topOrigin` is not parsed;
  - credential-ID length is checked only for being non-empty (the spec maximum is 1023);
  - the COSE key length is found by decoding and re-encoding CBOR, which is fragile on non-canonical input;
  - a known-bad EdDSA map header is patched.
- **M** Dart crypto:
  - `pointycastle` 4.0.0 is pure Dart. ECDSA verify range-checks r and s (`ecdsa_signer.dart:134-142`), and RSA PKCS#1 v1.5 does a full DigestInfo compare (`rsa_signer.dart:110-133`). It has **no Ed25519**.
  - `cryptography` 2.9.0 has pure-Dart Ed25519 verify (`lib/src/dart/ed25519.dart:110`). Its pure-Dart ECDSA and RSA **throw UnimplementedError**.
  - `webcrypto` 0.6.1 uses BoringSSL over FFI with build hooks and needs cmake and a C compiler. It has ECDSA and RSA but **no Ed25519**. AOT cross-arch Docker behaviour is **U**.
  - `cbor` 6.5.1 `cborDecode` throws unless exactly one item (`decoder.dart:44-62`), and authData puts the COSE key and the extensions back to back.
- **M** `passkeys_server` 1.0.0 on pub.dev (LunaONE GmbH, publisher `timm.preetz.xyz`, BSD-3, 2025-09-29, 0 stars, last push 2025-10-01):
  - Registration checks only the key ID, rpIdHash and challenge. It skips clientData type, origin, UP/UV, ID length, attestation and the allowed-algorithm list.
  - Login checks only the challenge and the signature. It skips type, origin, rpIdHash, UP/UV and signCount.
  - It supports ES256 and RS256 only, with no EdDSA. `derToRawSignature` silently truncates r or s longer than 32 bytes.
  - It has two tests.
  - The other pub.dev "webauthn" packages are client or authenticator side.
- **M** `tests/test_passkey_endpoints.py:57-135` has a **software authenticator** (P-256, fmt none, real flags, DER signatures, cbor2) that drives the real endpoints, with no webauthn mock. It is the only wire-level WebAuthn oracle we own.

## B. Failure modes others already hit

- **Shared-database strangler (I, general practice).** The usual failure is not SQL contention but **invariants held in process memory**: caches, connection registries and dedupe sets that one side updates and the other never sees. Here that means the Hub, echo, the rate limiter and the provider-token caches (A2). Teams that split by route on a shared DB typically discover the problem as "a ban didn't kick the socket" or as duplicate messages.
- **Two subscribers to one event stream (I).** When old and new both consume the bus, each persists every event. Idempotency keys (#42) are the usual prerequisite. Content-keyed echo dedupe (ours) is exactly the stand-in that breaks across processes.
- **SQLite multi-process writers (M, drift issues; I, SQLite docs).**
  - Deferred transactions that later upgrade to write get SQLITE_BUSY that busy_timeout does not retry (#3794).
  - WAL BUSY_SNAPSHOT poisons the cached statements (#3830).
  - In rollback-journal mode, readers block writers' commits.
  - Drift's default busy_timeout is 0.
- **ORM to drift on a DB the ORM built (M, probed).**
  - `onCreate` runs on an existing DB, or `createAll` silently no-ops.
  - The date format differs (`' '` vs `'T'`, integer mode throws).
  - Drift adds a BOOLEAN `CHECK` the source lacks.
  - Default spelling and table-constraint order fail validation.
  - `validateDropped:false` hides extra or missing indexes.
  - The snapshot exporter dropped CHECKs (#3219), and step migrations ignored `customConstraints` (#3694).
  - `alterTable` rebuilds from the Dart definition, so anything not reproduced verbatim (named CHECKs, `DEFAULT '0'`) is silently lost.
  - No upstream precedent was found for alembic→drift adoption (searched drift issues for "alembic", "existing database user_version").
- **WebAuthn server bugs (M, advisories).**
  - CVE-2021-38299 (PHP web-auth): missing user-presence check.
  - CVE-2026-30964 (web-auth <5.2.4): origin matched on host only.
  - GHSA-h4fw-6r7f-w494: UV policy taken from the client request.
  - CVE-2023-45669 (webauthn4j-spring): counter not persisted.
  - SimpleWebAuthn 2026: GHSA-6hxq-p678-4hr2 (attestation certificates not chained to a root), GHSA-j3h4-m3m2-7p7j (SSRF via certificate URLs), GHSA-2g3p-m8c9-hhwh (CRL cache poisoning).
  - fido2-lib GHSA-g3qj-j598-cxmq (CBOR heap over-read).
  - Java "psychic signatures" CVE-2022-21449 (r=s=0 accepted; I, not fetched).
  - `passkeys_server` itself is an example of a server that checks almost nothing (A4).
  - Our own: uncaught sibling exceptions produce 500s (A4).
- **"Type-safe port" over parsed values (M, `docs/design/15-TEMPER.md`, cited in CRUCIBLE).** Types protect values you construct, not values you parse. The bus payloads, the share values (a66 hands over a Python repr in incremental updates) and WebAuthn CBOR are all parsed.
- **Version-skew blindness (M, A1).** CI exercises master/main while prod runs the Feb/June pins. A port validated only in CI would be validated against `chat_server:1` plus S-expr payloads, a combination prod does not emit. The island already lives with this.
- **Mixed-runtime images (I).** Image size and attack surface are set by the largest runtime present. A Dart gateway in an image that still carries Python for the registrar, the ChatServer, migrations and seed-building saves little (A5). The common failure is a "Dart" image that still ships the full Python stack because one role was overlooked.

## C. Solution space and prior art (HELD BACK from Spark; for Cast only)

**Bus**
- Observer, not Actor: `BusProcess` (service id 0, no registration) plus `ServicesCache.changes` filtered by `ServiceFilter(name:'chat_server')` with protocol `*`, `TopicRouter` per-channel handlers, `ECConsumer` on `{server}/control` with filter `channel_list`, and `bus.send('$path/in','send_message',[u,[ch],text])`. Payload tiers: S-expr, then JSON, then bare.
- Parity check: run against the local rig, which already IS the prod pin (A1), and against master in CI. Add a live `send_message` round trip to `observer_acceptance.sh` (never exercised).
- Pin `aiko_services_dart` by git SHA as a path or git dependency until the licence is settled. Or vendor the ~1.5k lines actually used (codec, transport, services_cache, ec_consumer, router) under the island's AGPL. That vendoring is the licensing question for Andy, and it does not go away.

**Seam / sequencing**
- Caddy already fronts the gateway (`deploy/caddy/Caddyfile`: a single `reverse_proxy localhost:8095`). Path matchers (`handle /v1/well-known/*`, …) give a route split for read-only GETs with no other moving part.
- Strangler order the measurements allow: (1) read-only GET families; (2) push worker (device_tokens reaper already race-safe; needs a trigger: a DB poll on `messages`, a local socket, or the bus); (3) build #46 (session-reconciliation sweep, CAST exists) and #42 (`UNIQUE(channel_id, client_msg_id)`) before moving any writing route or the WS. Or skip the strangler: move WS, bus ingest and writing routes as one unit (the "core"), keeping Python only for the routes not yet ported.
- Parallel-run or shadow (GitHub Scientist style): mirror read-only requests to Dart and diff responses. That is safe because GETs do not write.

**Schema**
- Keep alembic as sole authority (ISL-0001) during the port. Drift opens with `setup` asserting `alembic_version` and setting `busy_timeout=5000`, plus `enableMigrations:false` or `schemaVersion` = 28 stamped. Hand-faithful table definitions (`customConstraint`, `CustomSqlType('DATETIME')`, a custom `IslandDateTime`), with `validateDatabaseSchema(validateDropped:true)` against a seed built by the real alembic, run in CI.
- At cutover, a new ADR moves authority to drift: freeze 0028 as drift v28, generate the snapshot, then `make-migrations` from there. Or follow the app's pattern: no codegen, raw-SQL DDL with a `table_info` comparison test (simpler, but loses typed queries).

**Images**
- Split the image per role: `aiko-bus` (Python: registrar plus ChatServer at the pins) and `aiko-chat-island` (Dart AOT on distroless/cc). Both are attested on the index digest with the same `release.yml` merge/attest pattern. Or keep one image during the transition, with both runtimes.
- Or `dart build cli` for native assets (sqlite3 hooks). Verify cross-compilation from one runner, else build natively per arch (the runners exist already).

**WebAuthn**
- Pure-Dart stack: `pointycastle` (ES256 with strict DER→(r,s) and range checks; RS256 with a minimum 2048-bit modulus), `cryptography` Ed25519, `crypto` SHA-256, and a narrow hand-written CBOR/COSE/authData parser (definite-length only, depth and size limits, returns the consumed length so the original COSE bytes are stored).
- Checks to implement beyond py_webauthn: reject `crossOrigin:true` and any `topOrigin`; credential ID ≤1023 bytes; one root error type mapped to 4xx. Derive `android:apk-key-hash:` origins from the fingerprints. Accept fmt none plus packed self-attestation, and decide others after measuring `aaguid` in prod.
- Vectors:
  - W3C WebAuthn L3 §16 test vectors (none-ES256, packed-self, crossOrigin, topOrigin, long credential ID, ES256/384/512, RS256, Ed25519);
  - go-webauthn `protocol/specification_vectors_e2e_test.go` (BSD-3) as a runnable precedent, plus its `fuzz_test.go`;
  - py_webauthn `tests/` real-device fixtures (BSD-3);
  - SimpleWebAuthn fixtures (MIT; it is the FIDO-conformance reference implementation);
  - our own software authenticator, as a Python-vs-Dart agreement test.
- FIDO conformance tools are free but gated by an access-request form (not open source).
- The parse round-trip of existing `public_key` rows (py_webauthn re-encoded COSE) must be a test.

**Test oracle**
- Wire harness: start the real binary (Python uvicorn or Dart) on a **seeded alembic DB file**, with settings from env, and APNs/FCM/JWKS/GitHub/LiveKit base URLs pointed at local recording stubs. Mint tokens with the shared `JWT_SECRET`. Use a real WS client.
- First prove the harness against the Python binary (it converts ~23% of the suite and finds the lifespan-only bugs that per-test `FastAPI()` instances hide), then run it against Dart.
- Golden-vector extraction for codec, envelopes, signing and push planning (`test_seed_peer_vectors.py` pattern).
- An optional test-only control surface (`/__test__/reset`, clock), compiled out of prod builds.
