# ISL-0001: Alembic is the sole schema authority

## Summary

Every schema change reaches a database through an Alembic migration, hand-written,
and `alembic heads` must show exactly **one** head. Nothing else — not
`create_all`, not a hand-run `ALTER`, not a model change — is permitted to move a
database's shape.

## Motivation

Two failure modes, both survived, both expensive.

**Two heads merge clean in git and wedge boot.** Alembic's revision graph lives in
`down_revision` pointers inside Python files. Two branches each adding a `0006`
produce no textual conflict — git merges them happily — and the resulting
repository has two heads, which `alembic upgrade head` refuses to resolve. The
container's entrypoint migrates fail-closed before serving, so the symptom is a
production island that will not boot, discovered at deploy time. **Mergeable is
not correct**, and the version-control system cannot tell you the difference.

**SQLite is blind to several ALTERs.** It cannot drop a column, cannot alter a
CHECK constraint in place, and cannot change a column type. A migration written
against Postgres semantics silently does nothing useful, or fails, on the backend
production actually runs (ISL-0002). Today **13 of 21 migrations** use
`batch_alter_table`, which rebuilds the table (create new, copy, swap) — that is
not an exotic case, it is the normal case here.

## Proposal

1. **One head, always.** `alembic history` shows a single head; a second one is a
   defect to fix before merge, not after.
2. **Hand-written, never autogenerated.** A migration is a point-in-time record
   and must not import evolving model code. Column shapes and CHECK literals are
   hardcoded in the migration and kept in sync with `domain/models.py` by parity
   tests (`test_migrations_match_models` for tables; a structural assertion in
   `test_migrations` for CHECK sets).
3. **`batch_alter_table` for anything SQLite cannot do in place** — dropping a
   column, changing a CHECK, retyping. Assume you need it unless you have checked.
4. **The entrypoint migrates fail-closed.** A bad migration keeps the container
   from serving rather than serving against a half-shaped database.

## Rationale and alternatives

- **Why not `create_all` in dev and migrations only in prod?** It splits the
  schema into two authorities that drift, and the drift surfaces as a migration
  that works locally and fails in production — the exact class this ADR exists to
  remove. Dev runs the same migration chain.
- **Why hand-written rather than `--autogenerate`?** Autogenerate imports live
  models, so the generated migration describes the models *as they are today*.
  Re-running it later against changed models produces a different migration for
  the same revision id. A record that changes retroactively is not a record.
- **Why not enable multiple heads and merge them?** Alembic supports merge
  revisions, and they work. The objection is not mechanical: a merge revision
  hides that two people changed the schema without seeing each other's change,
  which is the thing worth catching.

## Consequences

An additive-only lint over migrations is a natural gate on top of this invariant,
and it is the acknowledged blocker for automated deploy — see
`docs/crucible/reactive-deploy/` and tracker #3188 / #2615. Image rollback cannot
undo a forward migration, so *"does this release change the schema?"* has to be
answerable mechanically before an island can safely pull one unattended.
