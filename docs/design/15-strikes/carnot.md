## CarnotCodeCarver's Design Strike

**Verdict:** DISSOLVE

**Summary:** No real engine matches the Carnot cycle; a reviewer's job is to say how far short we are. This design is short by its own thermodynamic accounting: it spends a new image/shim/language contract to move only the already-isolated 334 lines, while the actual ISL-0003 failure class remains in the unsyncing shim and in non-image artifacts. The premise should dissolve into the v2 declarative deploy path: make the box state a shipped, versioned cohort from the control side, and stop trying to teach the image to police deploy machinery it cannot own. Dijkstra: "Simplicity is prerequisite for reliability."

**Fatal flaws:**
- The design fails its own Question 5. Moving 334 uncontested lines out of 2,373 is not enough heat-work conversion to justify a new language boundary, a shim contract, image-internal tooling entrypoints, and cross-version compatibility rules on the sovereign box deploy path. That is entropy added to reduce entropy.
- It mistakes line-count shrinkage for closure of ISL-0003. The class was not 'too much shell'; it was 'the thing that must enforce drift is itself unsynced.' A versioned shim improves observability but still requires the one manual sync whose absence caused the limit. Smaller unsynced surface is not a closed cycle, just a colder exhaust.
- The dissolving alternative is already in the bundle: declarative deploy v2. Control-side whole-file shipping of compose, update.sh, mosquitto config, and complete encrypted .env gives the operator a versioned cohort and removes the stale-box-artifact problem directly. The image does not need to carry deploy policy to make box deploy policy sync.
- The design under-counts the language-boundary blast radius. Dart-in-image means every moved predicate now has two interfaces: the stable bash shim invocation and the internal typed implementation. The hard part becomes compatibility, packaging, entrypoint discovery, error taxonomy, attestation gating, and first-pull/bootstrap behavior. That is not free work; it is a new thermodynamic reservoir.
- The proposed first increment is framed as low-risk because behavior does not change, but that weakens the case for doing it. If the three pure scripts are already isolated and tested, then rewriting them first proves mostly that a rewrite can preserve known behavior. It does not attack the outage-producing compose drift path.
- The shim version handshake is necessary but not sufficient. An old shim that lacks the handshake cannot be made to fail closed by the new image, because it will never ask. That is exactly ISL-0003's limit replayed. The design names this but then proceeds as if contract design can reach backward in time.
- The drift-check argument in §4 is clever but creates a security coupling the document cannot pay for. Pulling the new image before drift refusal changes the trust order: new deploy artifact can participate in certifying its own deployment unless the shim verifies attestation first. Today attestation is present, not verified. Feynman: "The first principle is that you must not fool yourself."
- The option frame is still wrong after the three-home correction. The real alternatives are not just 'box vs image vs control side'; they are 'make box artifacts self-updating by deployment' versus 'leave a permanent on-box executor that must reason about freshness.' The design picks the latter, then adds machinery to monitor the wound.
- It preserves the most dangerous coupling: deploy correctness depends on choreography between files whose update mechanisms differ. The image updates by pull, the shim by manual sync, .env by control-side secret flow, compose by separate artifact handling. The reversible process would make one cohort advance or refuse as a unit.
- The success criterion is too local. '334 lines moved' optimizes the source-location of helper predicates, not the operator outcome: a release with compose/config/deploy-script changes arrives safely, atomically, and observably on a shared sovereign box. Hamming: "The purpose of computing is insight, not numbers."

**What holds:**
- The three-home framing is valuable. Control side, image, and box do have different binding constraints, and the design correctly rejects the original two-home issue frame.
- The rejection of putting update.sh orchestration inside a container with the Docker socket is sound. On shared multi-tenant boxes, docker.sock is root-equivalent authority; calling that a sovereignty regression is correct.
- The distinction between REFUSED, PASSED, and COULD NOT RUN is excellent. A check that cannot distinguish 'passed' from 'did not execute' is exactly the predicate/lifecycle bug class this system has repeatedly hit.
- The design is honest that Dart helps closed-set decisions, not parsers. That restraint matters; types do not sanctify parsed reality.
- The caution against automatic reactive deploy is correct and preserves the prior Temper fatal. This design does not itself reintroduce unwatched auto-deploy, and the constraint that the image never initiates deploy is worth keeping.
- The drift-check observation that 'before pull' is thrift while 'before backup/recreate' is safety is plausible. But it remains subordinate to the trust-order problem and should not carry the design.

**If RECAST, what to fold back:**
- Dissolve Increment 1 as a rewrite project. Keep the extracted decision scripts where they are unless a concrete defect, test gap, or packaging need demands movement. Pure predicates can be tested in shell or wrapped without crossing the image boundary.
- Fold the useful contract ideas into the box/control deploy path: every operator-facing command should produce REFUSED, PASSED, or COULD NOT RUN; COULD NOT RUN fails closed; version reporting is explicit.
- Recast around declarative deploy v2 as the main fix for ISL-0003: control-side decrypt, ship a complete generation containing compose, update.sh, mosquitto config, and .env, atomically flip current, then run update.sh. That attacks the unsynced artifact class instead of relocating helper logic.
- If attested-image deploy tooling is still desired later, require a prior invariant: the shim verifies image provenance before executing any image-provided deploy helper. Without that, image-resident refusal logic is self-certification.
- Separate 'reduce deploy toil' from 'move code into image.' The low-entropy path is a watched one-command sequenced deploy that ships the cohort and invokes the existing box executor, not a new internal deploy API inside the product image.
- For standup.sh, only move post-pull decisions after the cohort deploy problem is solved. Bootstrap is not the right first battlefield; it is where reversibility is lowest and hidden assumptions are hottest.
- For compose drift, prefer eliminating drift by whole-cohort shipping over detecting drift from the artifact being deployed. Detection is a guard; cohort authority is the simpler thermodynamic cycle.
- Keep update.sh as the shim spine, but make its freshness supplied by the control-side generation mechanism rather than by an image minimum-contract negotiation that old shims cannot understand.
